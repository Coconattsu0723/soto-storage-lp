# soto Implementation Rules

## 0. 文書の役割

実装時に守る技術・レスポンシブ・アクセシビリティ・インタラクションの正本。本書は実装方針のみを定め、HTML / CSS / JavaScriptのコードは含めない。

## 1. 技術要件

- HTML5
- CSS3
- Vanilla JavaScript
- モバイルファースト
- フレームワークは使用しない。必要性が新たに生じた場合は、ユーザー確認後に判断する。
- JavaScriptが動作しない場合でも、サービスの主要情報を読めるようにする。
- JavaScriptは装飾ではなく、Navigation、FAQ、Simulator、Formなどの操作補助に限定する。

## 2. Semantic HTML

- ページ構造に応じて`header`、`nav`、`main`、`section`、`footer`等の意味を使い分ける。
- 見た目の都合だけで要素を選ばない。
- リンク遷移にはリンク、状態変更・開閉・実行にはボタンを使う。
- 料金やBOX比較は、読み順と比較のしやすさを優先した構造にする。
- リストとして意味のある項目はリスト構造を使用する。
- CSSを外した状態でも、情報の順序と意味が通るDOM順にする。

## 3. Heading Structure

- `h1`はHero Main Copyの1つだけに使用する。
- 主要セクションは`h2`を使用する。
- セクション内のカードや小項目は、階層に応じて`h3`以下を使う。
- 見た目のサイズ調整を目的に見出しレベルを飛ばさない。
- 英字ラベルを装飾テキストとして扱う場合、見出し階層を重複させない。
- ロゴ画像をページの`h1`代わりにしない。

## 4. CSS設計

### CSS Custom Properties

以下をCSS Custom Propertiesで一元管理する。

- ブランドカラー
- 文字色、背景色、境界色
- Font Family
- Typography scale
- Spacing scale
- Border Radius
- Container width
- Transition duration / easing
- z-indexの用途別段階

数値は`02_DESIGN_RULES.md`の確定・候補区分を守り、未確定値を正本として扱わない。

### Class方針

- 共通パターンとセクション固有スタイルを区別する。
- 見た目だけに依存する名前を避け、役割が分かる命名にする。
- 詳細度を上げすぎず、上書き前提の複雑なセレクタを避ける。
- JavaScriptの参照先は、可能ならスタイル用クラスと役割を分ける。

### Grid / Flex

- 2次元のカード配置、比較表、Before / After等はCSS Gridを基本候補とする。
- 1方向の整列、ボタン内、ナビゲーション、ラベルと値の組合せ等はFlexboxを基本候補とする。
- DOM順を不自然に入れ替えるためにGrid / Flexの視覚順序を使わない。
- コンテンツ量の変化に耐える配置にし、固定高へ依存しない。

## 5. Responsive

### 進行順

**375 → 390 → 768 → 1024 → 1366 → 1440px**

375pxを整えてから上位幅へ進む。確認幅ごとにmedia queryを作らず、レイアウトが破綻する地点・構造が変わる地点だけにブレークポイントを設定する。

### 375px

- 1カラム中心。
- 写真の世界観と文章の理解を優先する。
- Storage Simulatorは縦積み。
- CTAとForm操作に十分なタップ領域を確保する。
- 横スクロール、長い英数字、料金、寸法表記の折返しを確認する。

### 390px

- 375px確定後に、コピーの改行、左右余白、カード、画像、CTAを確認する。
- 390px専用設計に分岐させない。

### 768px前後

- 内容に応じて2カラム化する。
- Flow、Before / After、BOX / Price、カード群の一覧性を高める。
- タブレットがタッチ端末である可能性を前提にする。

### 1024px以上

- 写真 + テキストの左右配置を使用できる。
- コンテンツ幅を広げすぎず、外側の余白と読みやすい行長を保つ。
- 1366px / 1440pxで過度な引き伸ばし、画像の主題切れ、間延びを確認する。

### 全幅共通チェック

- 横スクロールがない。
- 見出し・コピーに不自然な改行や孤立した短い行がない。
- Navigation、CTA、Form、FAQ、Simulatorを操作できる。
- 写真の人物・家具・BOX等の主題が切れない。
- before / after、料金、寸法、Simulator結果が誤読されない。

## 6. Accessibility共通要件

- 文書言語を日本語に設定する。
- キーボードだけで全操作を完了できる。
- `focus-visible`を視認できる形で表示し、独自スタイルで消さない。
- タップ / クリック対象に十分な操作領域と間隔を確保する。
- 色だけで選択、エラー、成功、開閉状態を表現しない。
- 文字、UI、フォーカス表示のカラーコントラストを確認する。
- 意味のある画像には内容と役割に合う代替テキストを付ける。
- 周辺テキストと重複する装飾画像は空の代替テキストにする。
- 視覚上の並びとスクリーンリーダーの読み順を一致させる。
- 自動スコアだけで判断せず、キーボード、拡大、読み順、エラー操作を手動確認する。

## 7. Navigation

- 主要セクションへのページ内導線を基本とする。
- 正式なリンク名は`01_CONTENT_STRUCTURE.md`の要確認事項として、実装前に確定する。
- 現在地表示を行う場合、色だけに依存しない。
- 固定Headerを採用する場合、アンカー移動後に見出しが隠れないようにする。
- SPメニューを開閉する場合、開閉ボタンに対象との関連と開閉状態を持たせる。
- メニューはキーボードで開閉でき、開いた後のフォーカス移動が自然であること。
- Escapeで閉じられるようにし、閉じた後は開閉ボタンへフォーカスを戻す。
- 背景スクロール制御やフォーカス管理が必要な方式を選ぶ場合は、実装時に挙動を検証する。

## 8. CTA

- ページの最終CVは保管BOXの申込みに統一する。
- CTA文言は正式コピーを使用し、一般的な「送信」「こちら」へ置き換えない。
- ページ内移動やURL遷移はリンク、Simulator開始やForm送信等の処理はボタンとして実装する。
- Hero、Simulator結果、Final CTAの行き先と役割を混同しない。
- 料金や条件を隠したまま申込みを強制しない。
- sticky CTAの採用は未確定。採用する場合、本文・Form・ブラウザUIを覆わないことを確認する。

## 9. FAQ Accordion

- 各質問はボタンとして操作できる構造にする。
- 開閉状態と対応する回答領域の関係を支援技術へ伝える。
- キーボードのEnter / Spaceで操作できる。
- フォーカス表示を保つ。
- 回答内のリンクへキーボードで到達できる。
- JavaScriptが動作しない場合にも回答内容へ到達できるフォールバックを設ける。
- 開閉アニメーションは内容の読み上げや操作を妨げない。
- 複数同時に開けるか1つだけ開けるかは未確定。ユーザー確認後に統一する。

## 10. Storage Simulator

### 入力

- 4問を明確なグループとして示す。
- 各選択肢にはクリック可能なテキストラベルを付ける。
- 同一質問内は単一選択とする。
- 選択状態を色だけで表現しない。
- 未回答の質問がある状態で判定するか、回答を必須にするかは正式確認する。

### 判定

- Q1〜Q4のスコアを合計する。
- 0〜1：STANDARD BOX × 1
- 2〜3：STANDARD BOX × 2
- 4〜5：STANDARD BOX × 3
- 6〜8：STANDARD BOX × 4
- 月額は推奨数 × 660円（税込）で表示する。
- BOX配送・初回集荷0円を補足する。
- 判定ロジックと表示料金を別々に手入力して不整合を起こさない設計にする。

### 結果通知

- 結果は視覚的に明確な見出しとともに表示する。
- 操作後に追加された結果を支援技術が認識できるようにする。
- フォーカスを強制移動する場合は、ユーザーの読み位置を不自然に奪わないか検証する。
- Result Characterは装飾補助とし、結果の数値を画像だけで伝えない。

### 申込み値への引き継ぎ

- 「このBOX数ではじめる」で申込みエリアへ移動する。
- 判定したSTANDARD BOX数量を申込みの初期選択値へ反映する。
- ユーザーは移動後にBOX種類・数量を変更できる。
- 申込み側に引き継がれた内容をテキストで確認できるようにする。
- Simulatorを使用しないユーザーも直接BOXを選択して申し込めるようにする。

## 11. Form Accessibility

- すべての入力項目に視覚表示された`label`を付ける。
- 必須 / 任意をテキストで明示する。
- 入力形式、単位、例、制約を入力前に理解できるようにする。
- エラーは該当項目の近くに具体的な修正方法として表示する。
- エラー状態を色だけで示さない。
- 送信失敗時に入力内容を不必要に失わない。
- 送信時にエラー概要を示す場合、各該当項目へ移動できるようにする。
- 完了メッセージを支援技術へ通知し、次に何が起こるかを説明する。
- 住所、連絡先、カード情報には適切な入力補助を検討する。
- 自動入力を妨げない。
- 支払い情報の実処理方法は未確定。ポートフォリオ用の架空フォームで実データを取得しない方針を別途確認する。
- 利用規約・プライバシーポリシーへの同意は、リンク先と選択状態をキーボードで確認できるようにする。

## 12. Images

### Loading

- Heroの主要画像は初期表示を優先し、安易に遅延読み込みしない。
- ファーストビュー外の写真・イラスト・アイコンは、表示影響を確認したうえで遅延読み込みする。
- 画像の幅・高さ情報を持たせ、読み込み時のレイアウトシフトを抑える。
- 原本は残し、公開前に適切な解像度のWebP等の派生画像を作る。

### object-fit / aspect-ratio

- 写真の枠比率を用途ごとに定め、レスポンシブで不自然に変形させない。
- 写真は比率を維持し、人物・家具・余白などの主題が切れない位置を設定する。
- BOX、アイコン、ロゴ、キャラクター等の透過素材は、全体が見える表示を基本とする。
- Before / Afterは比較を誤解させないよう、表示面積・比率・視点をそろえる。

## 13. Motion / prefers-reduced-motion

- 動きは操作結果や視線誘導を補助する範囲に限定する。
- 大きな移動、長いパララックス、点滅、過剰な自動再生を使わない。
- `prefers-reduced-motion`が有効な場合、不要なアニメーションとスムーズスクロールを抑制する。
- 動きを止めても情報や操作が失われないようにする。

## 14. Performance / SEO準備

- 写真をWeb表示に適した解像度・形式へ最適化する。
- 未使用素材を読み込まない。
- Fontのweightや文字セットを必要以上に増やさない。
- `lang`、`viewport`、title、meta description等は公開前に確認する。
- 正式公開URLが決まる前にcanonicalやOGP URLを仮設定しない。
- OGP / faviconは公開前の後工程で制作・設定する。

## 15. 実装時の検証項目

- JavaScriptなしでも主要情報を読める。
- Heroだけが`h1`で、主要セクションが`h2`になっている。
- キーボードでNavigation、FAQ、Simulator、Form、CTAを操作できる。
- 200%拡大、文字拡大時に情報や操作が欠けない。
- 375 / 390 / 768 / 1024 / 1366 / 1440pxで横スクロールがない。
- Simulatorの境界値0、1、2、3、4、5、6、8で正しい結果になる。
- 推奨BOX数、月額料金、申込み初期値が一致する。
- FAQの開閉状態と回答の関連が支援技術へ伝わる。
- Formのエラーと完了状態が視覚・支援技術の両方で理解できる。
- Hero画像、Before / After、Final CTA Photoのトリミングがブランド世界を損なわない。

## 16. 実装前の要確認事項

- FormをLP内、別画面、モーダル、外部画面のどれにするか。
- ポートフォリオ上のFormが実送信かデモか。
- Navigationの正式項目とSPメニュー方式。
- FAQを複数同時に開けるか。
- Simulatorの未回答時挙動、再診断文言、結果表示文言。
- sticky CTAを採用するか。
- 正式ブレークポイント、Container、Spacing、Typographyの具体値。

これらをユーザー確認なしに実装判断で固定しない。
